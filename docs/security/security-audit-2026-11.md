# DevPack Security Audit (2026-11)

Scope: static review of `main` at commit `a492d7b`. Covers the two Supabase edge functions, the migrations (tables, RLS, storage), the frontend auth and upload paths, and a production dependency audit. No exploits were run, no requests were sent to the app or to Supabase, and no source code was changed.

## Status

Status of each finding as of this update. The findings below are the original 2026-11 review and are not edited.

- SEC-02 (attom-comps rate limit): Fix in PR #66

- SEC-07 (error detail leakage): Fixed. Clients get generic 503s, and auth-path throws return 401. Deployed.

- SEC-12 (password minimum): Client minimum raised to 8 characters. **Owner action:** set the Supabase Auth minimum password length to 8 in the dashboard; the repo does not control that setting.

- #16 (ErrorBoundary recovery): Already fixed. "Try again" resets the error state, covered by `src/components/__tests__/ErrorBoundary.test.tsx`.

## Summary

DevPack's core data model is sound. All six tables in the generated types have RLS enabled, the owner-only policies are correct, both edge functions validate the caller's bearer token before doing any work, and no service-role or OpenAI/ATTOM secret appears in `src/`. The main risks are in storage and cost control. The project-drawings and project-photos buckets are public and have a bucket-wide anonymous SELECT policy, so the storage listing API should let anyone enumerate every user's site photos and concept drawings (this needs a runtime confirmation). The `attom-comps` function has no per-user rate limit, so any signed-in user can drive paid ATTOM calls and unbounded writes through the service-role client. The `ai-generate` rate limiter is held in memory per isolate and does not cap prompt size. The production dependency tree has 13 high and 2 moderate npm advisories. **Overall risk: High.** The two High code findings (SEC-01, SEC-02) should be fixed before lender or investor data goes into production.

## Checked and OK

- **Secrets in `src/`.** No `service_role`, `SERVICE_ROLE`, `OPENAI`, or `ATTOM_API_KEY` string appears in `src/`. A regex scan of the repo for `sk-[A-Za-z0-9_-]{20,}` found no OpenAI-style keys. The `sk-` substring hits were false positives from "risk-" in names such as `risk-assessment`.
- **Service-role use.** Only `attom-comps/index.ts:152` creates a service-role client, and it reads the key from `Deno.env`. It is used only after the auth check, for `comp_cache` and `comp_lookups`.
- **Secret handling in functions.** `OPENAI_API_KEY` (`ai-generate:124`) and `ATTOM_API_KEY` (`attom-comps:213`) are read only through `Deno.env.get`. Neither appears in a response or a log message.
- **Auth on every request.** Both functions reject a missing or non-Bearer header with 401 (`ai-generate:79-86`, `attom-comps:146-147`), then validate the token with `supabase.auth.getUser` before any work (`ai-generate:88-100`, `attom-comps:148-150`). The OPTIONS preflight returns before auth, and only CORS headers are returned.
- **Input handling in `attom-comps`.** Strings are trimmed and length-capped (`str`, `attom-comps:21`). Numbers are coerced and checked for finiteness. The ATTOM and Census URLs use fixed bases with `URLSearchParams` or `encodeURIComponent`, so the request target cannot be changed by the client (no SSRF path). The Census and ATTOM calls have timeouts (6 s and 20 s).
- **`ai-generate` output clamp.** `max_completion_tokens` is bounded to 80-1000 (`:145`). The prompt is passed as a user message, and the system prompt constrains output. Upstream provider errors are logged server-side and not returned to the client (`:153-159`).
- **Generic errors.** Both 500 paths return generic messages (`ai-generate:174-178`, `attom-comps:291-294`).
- **Schema coverage.** The generated `types.ts` lists exactly six tables: `comp_cache`, `comp_lookups`, `developer_profiles`, `profiles`, `project_details`, `projects`. Each has RLS enabled in a migration. No table exists outside the migrations.
- **Owner-only RLS.** `profiles`, `projects` and `developer_profiles` have owner-only SELECT, INSERT, UPDATE and DELETE (or no DELETE on `profiles`). `project_details` checks ownership through the parent `projects` row for all four operations. UPDATE policies without an explicit `WITH CHECK` reuse their `USING` expression as the check, so a row cannot be moved to another owner's project or profile.
- **Service-only tables.** `comp_lookups` and `comp_cache` have RLS enabled and no policies, so anon and authenticated roles get no rows. Only the service role (which bypasses RLS) can access them.
- **Storage write paths.** `profile-assets` INSERT checks `(storage.foldername(name))[1] = auth.uid()::text`. `developer-headshots` uses the same check, and its UPDATE and DELETE policies match. `project-photos` and `project-drawings` INSERT and DELETE check that the first folder equals a project id owned by the caller. The client upload paths prefix with `projectId` or `user.id`.
- **`SECURITY DEFINER` function.** `handle_new_user` sets `search_path = public`.
- **Frontend HTML injection.** `dangerouslySetInnerHTML` appears only in `src/components/ui/chart.tsx:70`. It is a shadcn chart style block, and nothing in `src/` imports `ChartContainer` or `ChartStyle`, so it is dead code. No `innerHTML`, `eval`, or `document.write` in `src/`.
- **Stored links.** `company_website` is never rendered as an `href`. External `href`s in `FeasibilityForm.tsx:791`, `VisionMarketForm.tsx:619,840,849` are static literals. `NotFound.tsx:16` links to `/`.
- **Auth flow (`src/hooks/useAuth.tsx`).** The listener is registered before `getSession`, and the stale `getSession` result is ignored once the listener has delivered a session (`:21-50`). `emailRedirectTo` uses `window.location.origin` (`:57`). Client-side auth state is used only for routing. Data access is enforced by RLS.
- **Password reset (`src/pages/ResetPassword.tsx`).** The form shows only after a `PASSWORD_RECOVERY` event or a recovery hash with a live session (`:22-34`). A normal signed-in session does not see the form. `AuthModal.tsx:37` builds `redirectTo` from `window.location.origin`, not from user input.
- **Publishable key.** `src/integrations/supabase/client.ts:7` and the duplicate in `src/utils/unloadSave.ts:10` are the same key. Its JWT payload `role` claim is `anon`, so it is the public anon/publishable key and not a service key. Only the role claim was read.
- **Keepalive save.** `unloadSave.ts` sends the user's own bearer token, and the publishable key goes in the `apikey` header. Both go only to the Supabase project URL.
- **Tracked secrets.** `git ls-files` shows no `.env`, `*.pem`, `*.key` or credentials files tracked.
- **CSRF.** Mutations use bearer tokens in headers, not cookies, so cross-site form posts cannot carry the session.
